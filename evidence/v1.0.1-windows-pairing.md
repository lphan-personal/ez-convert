## The defect this run found (fixed before publishing)

First attempt used the installer from `3ecfdd4`. The pack was unzipped into a *different*
directory and adopted through `EZC_ENGINE_PACK` (the `adopt_pack()` path) — the image family died:

```
FAMILY image FAIL 0 120604 engine failed: step 1 (vips copy): engine killed (Timeout)
```

Cause: the 120 s per-invocation vips cap versus Windows Defender scanning the freshly written
vips tree. Measured on this host: **216,866 ms** for the first image conversion, 163 ms warm.

Fix (`13b9a43`): the vips cap is 600 s, pinned by a test, with `docs/ARCHITECTURE.md` §6.0.3, the
user guide's known-issue 13 and `docs/DETECTION.md` stating the same numbers. Rationale: the cap
is a hang guard, and a killed good conversion is worse than a long one.

## Cold first-touch cost per sidecar (separate fresh extraction, nothing pre-read)

```
second_extract_seconds 6
cold_vips_ms=89336
cold_ffprobe_ms=10891
cold_ffmpeg_ms=10881
cold_soffice_ms=2728
```

This answers the "is any other cap racing the AV scanner" question with a measurement rather than
a guess: `ffprobe`'s 30 s cap has ~2.7x headroom on first touch, `ffmpeg` has no fixed cap (stall
detector + 1800 s), `soffice` is 2.7 s. `vips` was the only program whose cap was inside the scan
cost, and it has been raised.

The same measurement varies by run — the earlier acceptance run on the same host put the cold
image at 216.9 s. Both are inside the 600 s cap; both are why the install notes state a first-run
expectation instead of letting a user read a scanner as a hang.

  on the VM for audit; the machine is a test box, not a user machine.
